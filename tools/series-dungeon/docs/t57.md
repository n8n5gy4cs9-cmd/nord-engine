## 2 What a camera is

The `camera` component on the `Camera` entity shows the part of the world around the entity's **position**. To follow something, move the camera entity. No special engine feature is needed, a script is enough.

Create `scripts/follow.js`:

@@code part3/follow.js@@

Add it to the `Camera` entity and leave the target at `Hero`.

* `lateUpdate(dt)` runs after every `update` and `fixedUpdate` of the frame. The camera must read the hero's position **after** the hero has moved, or it follows the previous frame and the picture shakes.
* **Bounds.** The camera centre may only go as far as half a screen from each map edge, otherwise we would see the void outside the level. `goalX` is the hero's x clamped to `[hw, width − hw]`.
* **Smoothing.** `x + (goalX − x) * k` moves a fraction `k` of the remaining distance each frame: quick when far, slow when near, which looks natural.

> **Why `1 - Math.exp(-stiffness * dt)` and not just `stiffness * dt`?** With `k = stiffness * dt` the camera follows differently at 30 and 144 frames per second, and above `1 / dt` it overshoots. The exponential form gives the same result for any frame rate, and `k` can never exceed 1. This one-liner is worth copying into every game.

## 3 Telling the camera how big the level is

The camera needs the map size, which only `Level` knows. Do not make the camera import the level: scripts should not be glued to each other. Use the **event bus** instead. At the end of `Level.start`:

```js
this.events.emit('level', { width, height });
```

and the camera listens for it in its own `start`:

```js
this.off = this.events.on('level', (size) => { this.bounds = size; this.snap = true; });
```

`this.events` is a game-wide message board: anyone can `emit` a named event with some data, anyone can `on` it. `on` returns a function that unsubscribes, which is why `onDestroy` calls `this.off?.()`. `this.snap = true` makes the first frame jump straight to the hero instead of sweeping across the map.

> **What if the camera script starts after the level has finished?** The level `await`s many spawns, so it always finishes later. If you ever need a guarantee, let the receiver ask instead: store the data on the sender and read it in `start`. For this series the order is safe.

## 4 Merging walls

Make the Level script a better citizen. The last version created one entity per `#`. This map has 449 wall tiles. Our row-by-row loop merges **horizontal runs** of walls into one wide entity:

@@code part3/level.js@@

* `let end = col; while (MAP[row][end + 1] === '#') end++;` finds where the run stops. At the end of a row `MAP[row][end + 1]` is `undefined`, which is not `'#'`, so the loop stops by itself.
* A run of `n` tiles becomes one wall of width `n * t`, centred at `col * t + w / 2`.
* `continue` skips the rest of the loop body, and `col = end + 1` jumps past the run.

The test script of this series counts the result: **74 wall entities instead of 449 tiles**. Fewer entities means fewer colliders to test every physics step, fewer sprites to draw and a smaller scene. A real engine does the same trick and calls it *greedy meshing* or *tile merging*. Merging vertically as well would shrink it further; try it as an exercise (hint: keep a grid of "already used" cells).

## 5 Check yourself

* Walk through the whole dungeon. The camera glides after you.
* Stand in the top-left room: the camera does not show anything left of or above the map.
* Set `stiffness` to 0 in the Inspector: the camera is rigid. Set it to 2: it lags like a lazy cameraman.
* Count walls in the Hierarchy: far fewer than tiles.

## What you learned

* A camera is an entity; follow with a script in `lateUpdate`.
* Frame-rate independent smoothing: `1 - exp(-rate * dt)`.
* The event bus (`events.emit` / `events.on`) decouples scripts.
* Merge neighbouring tiles into one collider and sprite.
