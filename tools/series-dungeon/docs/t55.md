This is the first part of a series about making a complete top-down dungeon game in Nord Engine, **without any Unity-style helper classes**: only the native `NordScript` API that every Nord project has. You write each script yourself and every line is explained. The series has six parts.

This tutorial assumes you can open the Nord editor and know what a variable and a function are. Nothing else. Allow 20 minutes.

**What you will build:** a blue square that you steer with WASD or the arrow keys, at the same speed on a slow laptop and a fast desktop, and that cannot leave the screen.

## 1 A new project

Start the editor and create a **2D** project called `dungeon`. From a terminal the same thing is:

```bash
nord new dungeon -t 2d
```

Open `nord.project.json`. It describes the whole project. We want a small, crisp screen that the engine scales to fit any window, and a world with no gravity because we look at the dungeon from above. Make `display` and `physics` look like this:

```json
"display": { "width": 640, "height": 360, "scale": "fit", "pixelArt": false, "background": "#14161c" },
"physics": { "engine": "arcade", "gravity": [0, 0, 0] },
```

(The editor's project settings edit the same values with fields instead of text.)

The same file lists the **input actions**: names that a script uses instead of key codes. The default project already has `left`, `right`, `up` and `down` mapped to both WASD and the arrow keys:

```json
"input": { "actions": { "left": ["KeyA", "ArrowLeft"], "right": ["KeyD", "ArrowRight"], "up": ["KeyW", "ArrowUp"], "down": ["KeyS", "ArrowDown"] } }
```

> **Why actions and not "is the A key down"?** A player can rebind actions, a gamepad can drive them and a phone joystick can drive them, and your script does not change. You will meet the same pattern in every game engine.

## 2 Scene: floor, camera and hero

Everything you see lives in a **scene**, `scenes/main.scene.json`. A scene is a list of **entities**. An entity is only a name, a position and a bag of **components** (a sprite, a collider, a camera…) and **scripts**.

Create three entities in the @ui[Hierarchy] with @ui[Create ▸ Sprite]:

| Name | Position (x, y, z) | Sprite size | Tint | Notes |
|---|---|---|---|---|
| `Floor` | 320, 180, **-5** | 640 × 360 | `#2e3440` | the background |
| `Hero` | 320, 180, **2** | 24 × 24 | `#88c0d0` | tag it `hero` |
| `Camera` | 320, 180, 10 | | | a **camera** component, zoom 1 |

> **What is the z value for?** In a 2D scene `z` decides what is drawn on top: a larger `z` is in front. The floor is at -5 so everything else covers it. The camera's own z does not matter for drawing.

The y axis points **down**, like on a web page. (0, 0) is the top-left corner of the world, so (320, 180) is the middle of a 640 × 360 screen.

Press **Play**. You see a dark floor and a blue square. Nothing moves yet.

## 3 The first script

Create `scripts/hero.js`. A script is a class that extends `NordScript`. The engine creates one instance for every entity that has the script attached and calls the methods you define:

```js
import { NordScript } from 'nord';

export default class Hero extends NordScript {
  update(dt) {
    // runs once per frame; dt is the seconds since the previous frame
  }
}
```

Select `Hero`, press @ui[+ Add script] in the @ui[Inspector] and choose `scripts/hero.js`.

You will use these methods over the series:

| Method | When it runs |
|---|---|
| `init()` | once, right after the script object is created |
| `start()` | once, when the whole scene exists (so other entities can be found) |
| `update(dt)` | every rendered frame |
| `fixedUpdate(dt)` | at a fixed 60 times per second, for physics |
| `lateUpdate(dt)` | every frame, after all `update` calls |
| `onDestroy()` | when the entity is removed |

## 4 Reading the keyboard

`this.input` gives you the actions. `this.input.vec('left', 'right', 'up', 'down')` returns `[x, y]`, each between -1 and 1:

```js
update(dt) {
  const [x, y] = this.input.vec('left', 'right', 'up', 'down');
  this.log(x, y);
}
```

Play and look at the @ui[Console]: `[1, 0]` while you hold D, `[-1, 0]` for A, and about `[0.71, 0.71]` for two keys at once.

> **Why is the diagonal 0.71 and not 1?** If a diagonal were `[1, 1]` the hero would move 41% faster diagonally, because the diagonal of a unit square is √2 ≈ 1.41 long. `vec` divides such vectors by their length, so the result never has a length above 1. Try to remember this one: it is the classic bug of beginner top-down games.

## 5 Moving: speed times time

Replace the body of the script with the final version:

@@code part1/hero.js@@

Walk through it:

* `static attributes` declares **editable fields**. `speed` appears in the Inspector under the script with a label, a default and a minimum. Change it while the game runs and the hero reacts. The values are saved in the scene, so you can have a slow hero in one scene and a fast one in another without touching the code. Read them as `this.attrs.speed`.
* `this.attrs.speed * dt` is the distance this frame. If the game runs at 60 frames per second `dt` is 0.0167, so the hero moves 160 × 0.0167 ≈ 2.7 pixels per frame, 160 pixels per second. At 144 frames per second `dt` is smaller and the steps are smaller, so the speed on the screen is the same. **Always multiply a speed by `dt`**; multiplying by nothing makes the game faster on faster computers.
* `this.entity.pos` is the entity's position `[x, y, z]`. You cannot change one number of the array in place; assign a whole new array, as the code does.
* `Math.max(12, Math.min(628, …))` clamps the position. The hero is 24 pixels wide, so its centre must stay at least 12 pixels from every edge. This is a temporary fence: in the next part real walls replace it.

Press **Play**, hold D for three seconds. The square slides to the right edge and stops.

## 6 Check yourself

* Hold W and D together: the hero moves diagonally at the same speed as straight.
* Change `speed` to 400 in the Inspector while playing: the hero gets faster at once.
* Open the project folder in a text editor: `scenes/main.scene.json` contains your three entities as plain JSON. Nord scenes are meant to be read and merged in Git.

If the hero does not move, click once inside the Game view: the game only receives the keyboard while it has focus.

## What you learned

* A project is a folder with `nord.project.json`, scenes and scripts.
* A scene is a list of entities; an entity holds components and scripts.
* A script is a class with lifecycle methods. `update(dt)` runs every frame.
* Input actions beat key codes. `input.vec` already normalises diagonals.
* Movement is speed × `dt`, always.
