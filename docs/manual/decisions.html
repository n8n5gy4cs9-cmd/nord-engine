Appendix / Nord Engine

Design decisions

Append new decisions at the bottom. Format: context → decision → consequences. Status: accepted | superseded.

ADR-001 Editor = Tauri v2 + web UI (PCUI), not egui — SUPERSEDED by ADR-013#

Context. Owner asked "egui as engine or copy from examples, if better" and "use some better UI", plus a full code editor with CodeMirror, vendored, thumbnails, docs with live code. Decision. Editor UI is HTML/JS (PCUI from PlayCanvas editor, CodeMirror 6, Lucide icons) inside a Tauri v2 shell with Rust backend. The viewport reuses Babylon/Phaser = true WYSIWYG. Consequences. + CodeMirror native, + docs/tutorials in the same stack, + testable in Chromium,

  • Win/Linux bundles come free. − Not a "pure Rust" UI. egui is still used for the Rust app runtime (ADR-010). Veto path: swap shell to eframe+wry; backend contract (ARCHITECTURE §4) stays.

ADR-002 Three runtime tiers sharing one scene JSON — accepted#

Phaser (2D JS), Babylon (3D JS), Rust/WASM (macroquad games, egui apps), plus a plain-HTML tier. Owner asked for Phaser+Babylon vendored and for wasm+webgl. Conformance examples must run on every tier that supports them.

ADR-003 Scripting = JavaScript first — accepted#

JS scripts hot-reload instantly and are what the huge snippet library is written in. Rust scripts only for wasm tiers. TypeScript optional later via vendored typescript/esbuild-wasm (not now).

ADR-004 Everything vendored, no CDN — accepted#

vendor/ committed; offline scanner enforces. Fonts too (bundle Inter + JetBrains Mono, OFL).

ADR-005 Upstream repos are harvested, not forked — accepted#

tools/fetch-upstreams.sh makes shallow/sparse clones into gitignored third_party/; useful files are copied into library/, examples/, docs/, editor/ with attribution in THIRD_PARTY.md; UPSTREAM.lock.json records SHAs. Do not vendor whole Godot (≈1 GB+). Godot/Defold UIs are not reused.

ADR-006 PRD.json is the source of truth for tasks — accepted#

task.md is generated by node tools/tasks.mjs render. Mark work with node tools/tasks.mjs done <ID>. CI/AI can run node tools/tasks.mjs check to detect drift.

ADR-007 No JS build step for editor/runtime — accepted#

ES modules + import maps. Only exception: one-off bundles (CodeMirror) produced by tools/vendor.mjs with esbuild and committed.

ADR-008 Mac wrapper via prebuilt player shell — accepted#

Prebuilt NordPlayer.app (wry+tao) + resource swap (ARCHITECTURE §7). Avoids needing Xcode/Rust on the user's machine per game.

ADR-009 Physics choices — accepted#

2D: Phaser Arcade (fast, simple) + Matter (rich). 3D: Havok (@babylonjs/havok, wasm). Rust: rapier2d (rapier3d later).

ADR-010 Rust/WASM: macroquad for games, eframe/egui for apps — accepted#

macroquad: tiny wasm, WebGL1/2, audio, no wasm-bindgen needed. Bevy is reference/examples source only (large wasm; maybe an M8 template). raylib: examples used as porting source for macroquad samples (raylib itself is C).

ADR-011 Licences — accepted#

Own code MIT. Vendored libs keep licences (Phaser MIT, Babylon Apache-2, CodeMirror MIT, PCUI MIT, Lucide ISC, rapier Apache-2, macroquad MIT/Apache, egui MIT/Apache). Godot icons CC-BY-4.0 need attribution if used. Defold ships a custom licence (Apache-based with extra terms) → inspiration only until reviewed. Re-verify each LICENSE at fetch time (fetch-upstreams.sh prints them).

ADR-012 Platform strategy — accepted#

Develop for aarch64-apple-darwin; use camino/dirs/std::path correctly, no hard-coded /. CI: macos-14 (Apple Silicon) first; Windows/Linux jobs added in M8 (allowed to fail until then).

ADR-013 Editor = native Rust egui (eframe + egui_dock) + embedded wry viewport; no Tauri — accepted (owner decision)#

Context. Owner prefers a native, lightweight Rust editor over a webview app, and asked for a full code editor. Games are JS (Phaser/Babylon) so a webview is needed for viewport/preview regardless; Tauri only added a web UI shell. Decision. nord-editor = eframe (wgpu/Metal) + egui_dock + egui_extras (images, SVG icons, syntect). The central viewport/Play/Docs panel hosts a wry child webview (edit mode of the vendored runtimes), synced with egui over IPC (ARCHITECTURE §4). Code editor is native (syntect highlighting + our own editing features); CodeMirror remains vendored only for the HTML manual's live examples. Mac wrapper uses a minimal wry+tao nord-player. Consequences. + fast, single Rust binary, native look, no web UI framework, easy cross-platform. − Must build a code editor on egui (no multi-cursor/LSP initially); − wry-in-egui embedding quirks (spike in M3-07; fallback = separate wry window); − editor UI tested via egui_kittest not Playwright. PCUI no longer vendored.

ADR: Skins + themes are data (assets/themes/themes.json), dark only (2026-10-12)#

A skin is a font pair (UI + code, ligatures on/off); a theme is a dark color set (UI colors + syntax colors). One JSON is the source for the JS runtime (generated module), the egui editor (include_str!) and the code editor. Light themes are deliberately not shipped for now. All fonts are vendored woff2 (OFL) — no CDN.

ADR-014 Editor ⇄ viewport/game bridge is HTTP/SSE through nord-serve, not wry IPC (M3, 2026-10-12)#

Context. The plan (ARCHITECTURE §4) used evaluate_script (down) and ipc_handler (up). That makes the whole editor loop depend on the macOS-only, unverifiable-in-sandbox webview embedding, and it can't be tested without a window. Decision. The dev server became a library crate nord-serve (used by nord serve and in-process by the editor). It owns a Hub: editor → page commands over SSE (/__edit/events, also injectable via POST /__edit/cmd), page → editor messages via POST /api/ipc, game console via POST /api/log (a tiny script injected into served HTML forwards console.*/errors). The embedded webview is then only a display surface for a URL. Consequences. + protocol fully tested headless (Playwright against the real nord serve), identical in the "Open in browser" fallback; + the webview spike (M3-07) shrinks to placement/resize/focus; − one local HTTP hop (negligible, localhost).

ADR-015 Undo = snapshot commands (M3, 2026-10-12)#

Scenes are small JSON trees, so every mutation goes through EditorState::edit(label, coalesce_key, f), which snapshots the entity list before/after and records a Command. Consecutive edits with the same key within 800 ms merge (a drag/slider = one step). Simpler and safer than hand-written inverse operations; cost is O(scene) per edit, fine at hobby scale. Autosave writes .nord-cache/autosave/… atomically and is offered for recovery on next open if newer than the scene file.

ADR-016 Code editor: own tokenizer, not syntect (M3, 2026-10-12)#

syntect's bundled grammars lack TypeScript, TOML, GLSL and WGSL, and its themes would not match themes.json. code/highlight.rs is a ~300-line tokenizer (JS/TS/Rust/HTML/CSS/JSON/MD/GLSL/WGSL/TOML) coloured from the shared theme's code palette, so web, editor and code editor share one palette. Limits: not a real parser (regex literals, nested template strings are approximations). egui_code_editor was evaluated on paper (no multi-cursor, fixed themes, no gutter hooks) and rejected; CodeMirror-in-webview stays the escape hatch.

ADR-017 2D edit view is Canvas2D, 3D edit view is Babylon (M3, 2026-10-12)#

The 2D edit view needs sprites/text/tilemap/collider outlines, picking and handles — not Phaser's renderer or physics. Plain Canvas2D starts instantly, is ~450 lines, and is trivially testable. 3D uses Babylon (GizmoManager, picking, glTF) so models/lights look right. The Game tab (Play) always runs the real Phaser/Babylon runtime.

ADR-018 One window for splash + main (M3, 2026-10-12)#

Splash is the same eframe window started borderless 640×360 and turned into the decorated main window (resize, centre, restore saved geometry) after ≥ 2000 ms. Avoids multi-window plumbing; tradeoff: a visible resize on slow compositors.

ADR-019 Rust/WASM tier: macroquad + rapier2d, scenes stay JSON, scripts are registry names (M5, 2026-10-12)#

crates/nord-runtime-wasm (games) and crates/nord-app-wasm (egui apps) are not workspace members (own [workspace], own lockfile): macroquad/eframe need wasm32 or native GL/audio libraries, so cargo build --workspace must keep working on a bare Linux box. The Rust runtime reads the same nord.project.json / scene / prefab / tilemap JSON as the JS runtimes (2D subset), so the editor, validation and export keep one data model. Scripts differ: scene entries say "path": "scripts/player" (or "player"); the file stem is a key into the Registry built in main (launch(Registry::new().register("player", …))). Everything referenced by JSON is preloaded before frame 1 (macroquad's asset loading is async). rapier2d is pinned to 0.22 (0.3x switched to glam and reshuffled the API; revisit when it matters), runs in metres (32 px/m) with y-down axes. Rendering is a thin manual world→screen transform (design size letterboxed into the canvas) rather than Camera2D, so pointer picking is trivial. Apps use eframe 0.31 + the wasm-bindgen CLI (trunk-free); dev builds land in <project>/target/web/ and the project's index.html loads them. Audio: macroquad's audio supports only .wav/.ogg (no mp3). Known harmless JS error in macroquad's bundle (register_plugin, quad_net section).

ADR-020 Desktop apps: wry shell for JS apps, native egui for Rust apps, one nord-desktop backend with a capability manifest (M9, 2026-10-12)#

Context. M9 wants real desktop apps (files, dialogs, notifications, tray, storage) from both tiers. Decision. All OS services live in one crate nord-desktop (Rust, no UI toolkit dependency). JS apps run in the existing nord-player wry+tao shell and reach it through a promise-based IPC bridge window.nord.desktop.* (origin-restricted to nord://game/; in the editor's Play the same API goes over nord-serve). Rust apps run as native eframe (not wasm-in-webview) and call a Desktop handle on Ctx; the wasm/web build falls back to browser APIs or returns Unsupported. Permissions are a least-privilege manifest (desktop.permissions in nord.project.json, baked into nord.json), enforced in nord-desktop so both tiers share one check; sensitive grants prompt on first use and are audit-logged. Tauri stays rejected (ADR-013). Consequences. + one implementation to test; + JS/Rust parity; − caps are an application-level guard, not an OS sandbox (macOS App Sandbox/bookmarks optional, M9-03); − macOS/Windows backends unverifiable in the Linux sandbox (CI matrix + owner). Details and checklist: docs/DESKTOP_APPS.md. Status: accepted & implemented (owner asked to proceed; defaults for the open questions: plain DOM apps, JSON KV store + optional SQLite, portable zip/tar.gz first, caps are not an OS sandbox).

ADR-021 PlayCanvas as optional 4th web tier (M8, 2026-10-12)#

Decision. web-3d-pc reuses the whole JS core (entities, scenes, scripts, input, audio, UI) with a thin runtime/playcanvas/ backend, exactly like Babylon: transform, mesh primitives, material, model (glb + animations), light, camera (free/orbit). Nord 3D data stays left-handed (Babylon convention) — the backend mirrors Z when writing transforms. Not supported yet (warned once): physics (rigidbody/collider/trigger), particles, postProcess, skybox, GUI. Not wired into the editor viewport (Scene tab stays Babylon); export + Play via nord serve only. Why optional: Babylon (+Havok) remains the default 3D tier; PlayCanvas is for owners who want its smaller footprint/renderer, and the vendor copy already existed. Bevy is offered only as a template (rust-bevy-game, wasm-app path), not as a runtime tier: it has its own ECS and does not read Nord scenes.

ADR-022 Current editor content by default, cached testing opt-in (2026-10-12)#

Context. Rebuilding the app shipped new example assets but the hub opened old private copies, hiding the newest content. The owner requires current content by default and an optional cached-content testing switch. Decision. Settings.use_cached_content defaults false. Examples/Tutorials open current engine-root files directly; saved-copy paths in Recent/launch arguments resolve to matching current examples. True opts into the former private-copy behaviour. Webviews use temporary storage when false and are recreated on mode changes; HTTP project responses always use no-store. Consequences. Rebuilt bundles show new assets without deleting saved copies. In default mode, edits/saves to bundled examples modify those source files; separate projects are the place for personal variants. Temporary game/browser saves last for the view; persistent storage and saved example copies remain an explicit testing option.

ADR-023 Optional audio entry and X-KOM campaign checkpoints (2026-10-13)#

Decision. Export an opt-in touchToStart(game, options) web helper; consume one activation/release and unlock audio without choosing a game screen. X-KOM explicitly installs it on the normal title path. Campaign saves reuse engine Save storage and serialize strategic data, not Phaser sprites/timers. Loading combat returns to HQ with the contact/final operation available to restart. A two-step Source Raid/Hive assault finishes the existing research/mission loop. Why. The owner wants safe first-touch title audio, reusable ready-made engine code, and a complete simple campaign with practical saving. Exact battle serialization would add fragile scene reconstruction for little benefit; HQ fallback was explicitly authorized. Other examples retain their own entry flow. Consequences. Save schema is versioned; obsolete/corrupt saves are ignored, title viewing does not overwrite a saved campaign, and interrupted tactical replays guard against a discarded scene. Saves use local browser storage, with pause-menu JSON export/import for backups and transfer between sites/devices (M6-33). Imports validate the X-KOM/version/checkpoint data before replacing the local campaign; combat checkpoints still resume at HQ.

ADR-023 — Separate learning paths from versioned underlying-engine references (2026-10-13)#

Decision: Keep one offline static HTML documentation site with Start here, Manual, Tutorials, Guides and API areas. Teach Nord entities, components and services first. Preserve and render the exact vendored Phaser/Babylon public declaration contracts in a labelled advanced engine library, with cloned upstream prose and the owner's older Phaser snapshot clearly versioned. Why: Beginners need an actionable route rather than a flat API catalogue; advanced users need complete underlying-engine contracts without being taught to construct a second Phaser/Babylon application alongside Nord. Versioned declarations prevent current source prose or an older crawl from silently becoming API truth. Consequences: No web framework or online dependency. Refresh scripts retain licences/source/hash metadata. Offline prose omits remote media/playgrounds, and Rust/native feature support still needs its own implementation/platform checks.
