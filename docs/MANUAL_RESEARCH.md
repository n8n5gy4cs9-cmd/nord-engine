# Manual redesign research

Researched 2026-10-13. These are original Nord recommendations based on the linked sources; no reference-site prose, artwork, or layout code was copied.

## What the reference sites do well

- **Godot:** the landing page offers entry points by experience level. Its introduction separates Getting Started, the feature Manual, advanced engine details, and the complete Class Reference. Search and grouped sidebar navigation give another way in. The first 2D tutorial states its result, shows the completed game, lists prerequisites, and explains why beginners should start with 2D. Nord should use similarly explicit learning paths and visible results. Sources: [Godot documentation home](https://docs.godotengine.org/en/stable/), [documentation organization](https://docs.godotengine.org/en/stable/about/introduction.html#organization-of-the-documentation), [first 2D game](https://docs.godotengine.org/en/stable/getting_started/first_2d_game/index.html).
- **Unity:** Manual and Scripting API are separate navigation destinations with their own search context. The manual also supplies breadcrumbs and previous/next links. Nord should make the difference between learning a feature and looking up a callable member visible at the top of every page. Sources: [Unity Manual](https://docs.unity3d.com/Manual/index.html), [Unity Scripting API](https://docs.unity3d.com/ScriptReference/index.html).
- **Roblox Actor:** the page begins with a compact method summary, linked parameter/return types, and inherited-member grouping. Each method has its own signature, parameters, returns, code sample, and jump target. Nord API pages should support both quick scanning and detailed reading, with stable links to individual members. Source: [Actor reference](https://create.roblox.com/docs/reference/engine/classes/Actor).
- **Tailwind theme:** the article introduces the concept, then pairs tiny examples with named source files and an explanation of their effect. A table maps namespaces to behavior. Nord examples should identify exactly which file to edit, explain what changes on screen, and follow code with a short explanation. Source: [Theme variables](https://tailwindcss.com/docs/theme).
- **Unreal coding standard:** examples contrast concrete code choices, and its documentation guidance asks for purpose, parameter units/ranges, return meaning, and caller-relevant warnings. Nord references should explain what an argument means, rather than merely repeat its type. Source: [Epic C++ coding standard](https://dev.epicgames.com/documentation/unreal-engine/epic-cplusplus-coding-standard-for-unreal-engine#exampleformatting).
- **n8n:** the official executions article defines the term in one sentence and then distinguishes modes with the actions that trigger them. This is a useful model for explaining Play, Preview, Export, and lifecycle events. Source: [Understand executions](https://docs.n8n.io/build/understand-workflows/understand-executions.md).

The requested [Mintlify n8n URL](https://mintlify.wiki/n8n-io/n8n/workflows/execution-modes) and [old NordScrap lifecycle URL](https://softa.site/nordscrap/docs/page.php?doc=api/script-lifecycle) could not be retrieved by the research browser. No claim about their current visual appearance is made. The user's preference for distinct semantic colors and a less convoluted sidebar remains an explicit design requirement. Godot's navigation was also inspected through browser accessibility state; visual screenshot inspection was unavailable in the background-agent browser.

## Recommended Nord structure

Use four primary destinations: **Start here**, **Manual**, **Tutorials**, **API reference**. Add Examples as a useful secondary destination. Show only the current destination's grouped navigation in the sidebar, and keep article headings in a separate on-page contents list. Search should include a destination label on each result so readers can tell a lesson from a reference entry.

Start here should answer: what Nord creates, what to install/open, where projects are saved, how to run an example, and how to make the first tiny change. Tutorials should be ordered, name prerequisites, show the result before the instructions, and provide a visible checkpoint after each meaningful step. The manual should explain individual tools and workflows in any reading order. The API should inventory the implemented public surface rather than mix member lists into beginner lessons.

Every major workflow needs a concrete beginner explanation. Optional **For dummy developers** blocks should use a small practical example and define unfamiliar terms immediately: a scene is a saved arrangement of objects; a script is a file of instructions; a frame is one screen update. Never hide required instructions inside those blocks. Use exact menu names and file paths, then explain the visible result and the most likely recovery action.

Use a calm dark surface, comfortable line length, clear headings, a restrained playful accent, and semantic colors with text labels: learning, API, tips, warnings. Color alone must not carry meaning. Put real Nord editor/game screenshots beside the task they explain, with captions describing what to notice; distinguish game previews from editor screenshots. Syntax highlighting, language/file labels, and copy buttons should use local vendored assets, with readable plain-code fallback.

## Complete API and upstream documentation

Nord's public runtime API should be generated from the implemented source and include signatures, member kinds, arguments, defaults, return types, lifecycle timing, units, relevant failures, examples, and links to related members. Inventory coverage must be explicit; third-party APIs must be labeled separately from Nord's wrapper API.

Babylon's official documentation source is [BabylonJS/Documentation](https://github.com/BabylonJS/Documentation), with articles in `content/` and static media in `public/`. Its repository uses [Apache-2.0](https://github.com/BabylonJS/Documentation/blob/master/license.md); the [documentation homepage](https://doc.babylonjs.com/) also states that its code examples use Apache-2.0 unless otherwise stated. For an offline copy, pin the source revision, retain its license/attribution and any NOTICE, record changed files, and keep Nord-specific notes clearly identified. The upstream website and remote playground widgets should not be required for offline reading.

The current official Phaser source is [phaserjs/phaser](https://github.com/phaserjs/phaser). Its README identifies JSDoc and type annotations as the source of API documentation and links the current [Phaser docs](https://docs.phaser.io/) (not retrievable in this research session). The source and associated documentation files use the [MIT license](https://github.com/phaserjs/phaser/blob/master/LICENSE.md). Preserve the complete notice when copying/generating documentation. Use the source matching Nord's pinned Phaser version. The old [photonstorm/phaser3-docs repository](https://github.com/photonstorm/phaser3-docs) explicitly describes itself as deprecated; it is not a current Phaser 4 reference. Prefer version-matched source JSDoc/types over that archive. Similarly label Babylon documentation's revision and API version, since its live manual may describe newer behavior than Nord's bundled runtime.
